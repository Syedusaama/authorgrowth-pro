# Release candidate security review

This document records design/code-review findings, not penetration-test certification. Real WordPress/database/SMTP/browser testing is still required (RELEASE-CHECKLIST.md).

- Book writes use native WordPress per-post capability checks and nonces. Launch metadata has its own nonce and autosave/revision guards. Private PDF uploads, settings, CSV exports, waitlist deletion and plugin review moderation require manage_options and action-specific nonces; review moderation additionally checks the parent-book edit permission and comment type.
- Chapter, waitlist and review forms validate published/unprotected book identity, nonces, field types/lengths, email, consent requirements and honeypots before writing. Nonces are not CAPTCHA or authentication for anonymous readers. Shared-IP/email hourly SQL counters fail closed for submissions; distributed bots can evade them.
- SQL values use wpdb prepared arguments/CRUD methods; table names derive only from the WordPress prefix and fixed plugin suffixes. Reports accept enumerated ranges/groups. Schema checks retry absent tables but table presence alone cannot detect every migration/index failure.
- Public book/review/title/attribute output is escaped; custom colors accept hex only. Reviews are plain text, pending by default, and approved-only on plugin displays. No synthetic review data is installed. Native comment plugins/administrative tools remain trusted actors.
- Outbound buttons read only editor-saved HTTP/HTTPS URLs, revalidated at redirect time. Visitor URL parameters are ignored. Preorder has a separate nonce purpose, typed destination and launch-time gate. This is not a retailer allowlist; authorized editors can choose external hosts. Redirects do not imply a safe third-party website, a confirmed visit or sale.
- Private PDFs require configured canonical storage outside known public roots, random filenames, path containment, upload/PDF MIME/signature checks and restrictive mode. Delivery opens the stored file, atomically consumes a hashed expiring bearer token, and emits attachment/no-cache/nosniff/no-referrer headers. Server aliases, malware scanning, filesystem administration, backups and HTTPS remain host responsibilities. Signed links can be forwarded or consumed by mail scanners.
- Only token hashes are stored. Waitlist confirmation and download consumption use conditional SQL updates. Mail failure invalidation is constrained to the token issued by that request, avoiding an older failure revoking a newer token. Simultaneous requests and failure recovery need real-database testing.
- Email sender values are validated; CR/LF header injection is rejected/removed. Plugin sender configuration does not alter site-wide mail. Tests use mail doubles; inbox delivery and SMTP provider configuration are unverified.
- Analytics stores aggregates, not IP/user-agent/email/cookie click events. DNT/GPC requests skip counting. Shared abuse counters store keyed hashes and are cleaned on requests/daily cron. Lead/waitlist/review privacy tools, documented consent and configurable retention are provided. Review erasure is registered before native comment anonymization to remove matching plugin reviews/metadata; verify integration order on staging with other privacy plugins.
- No uninstall-time deletion is performed. Daily retention can permanently remove data; settings explicitly state this, default verified-data retention is indefinite, and backups/external exports remain site-owner responsibilities. Approved reviews/private files are not auto-purged.

Report vulnerabilities privately to the repository owner through GitHub's private security reporting if available. Do not post reader data, tokens, credentials or exploit logs in a public issue. Include the plugin/WP/PHP versions and a minimal reproduction using test data only.
